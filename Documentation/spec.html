This is the working spec for the Axis And Allies Project: what it is, how it got here, what is built, and what is still undecided. Sections 1, 2 and 5 are the durable record — history, appended to as the project moves. Sections 3, 4, 6 and 7 are snapshots of files under .claude/ that will drift; each names its source.

1 · How this started

Miles — stated intent, as recorded in .claude/OPEN_QUESTIONS.md

"similar to Risk but slightly more complicated"

That single line is the whole design constraint, and it cuts both ways. It is why the game has a hex/territory map, a senate, doctrines and a card deck rather than Risk's single "roll dice, take territory" loop — and it is equally why the project is deliberately not a faithful Axis & Allies port. The official rulebook (A&A_40Anni_Rulebook_WEB.pdf) sits in the repo as reference. How binding it is has never been decided and is still an open question (§7).

The name confusion, resolved up front

The repo is called Axis And Allies. The game's internal name is Iron & Crowns — that is the <title> at index.html:6 and the header comment of all nine JS modules and server.js. There is no second project. An agent grepping the source for "Axis" and finding only "Iron & Crowns" has found the right code.

Two code trees, one repo

The repo contains two independent code trees: the live game at the root, and hexworld-v2/, a self-contained map-generation lab. They are not two generations of the same thing and they are not connected. This was mis-stated in the project's own docs until an audit on 2026-08-16 corrected it, and it is the single fact most likely to mislead someone new — the full treatment is in §4.

2 · Research digest

Civ V map architecture

civ5_map_architecture_deep_dive.md (162 lines) is a technical analysis of how Firaxis built Civilization V's map system, written as input to this project's map design. Its status is precise and worth stating carefully:

Superseded as the map-generation lineage only — still the live reference for the renderer. js/map.js:1 declares itself CIV 5 HEX GRID STYLE, and the corresponding entry in .claude/DECISIONS.md is PROVISIONAL, not superseded. Do not read "hexworld-v2 replaces this" as "the Civ V notes are dead."

What the notes established, and where each idea landed:

Civ V findingWhere it shows up here
Strict decoupling of plot coordinates (discrete q,r hex indices) from world-space rendering coordinates — logic stays predictable while visuals bend across cell lines The root game's core split: js/state.js holds discrete hex/territory state, js/map.js owns all geometry and pixels. It is also why js/data/mapData.js can place 26 territory seeds as plain q/r pairs.
Rivers and borders are edge features — stored as flags on the shared edge between two hexes, not inside a cell Adopted wholesale in hexworld-v2: rivers flow along hex edges via a junction graph, which is what makes every river end at a real coastline vertex.
Terrain blending, texture splatting, overlay features that overflow cell boundaries Reflected only as far as a 2D canvas/SVG renderer can go — terrain textures in images/tex_*.png, hybrid canvas/SVG drawing in js/map.js. The 3D/DX11 tessellation and shader material is background, not a build target.
Hit-testing and LOD as math rather than per-hex scene objects Independently arrived at in both trees — js/map.js does pan/zoom and hit-testing by hex-path math; hexworld-v2/CLAUDE.md records the same rule as a hard gotcha ("Hit-testing is math (pixelToCell), NOT per-hex interactive display objects").

Procedural world generation (inherited with hexworld-v2/)

hexworld-v2 was not researched for this project — it was built as a standalone lab and imported. Its research is recorded in its own spec (hexworld-v2/docs/v2-spec.html §2, and hexworld-v2/docs/DESIGN-SPEC.md). The short version: it started as a diagnosis of an earlier procedural hex generator that produced "diffuse" landmasses, "weird continents", and a sea-level slider that felt random. Each symptom traced to a root cause with a specific fix:

SymptomRoot causeFix as built
Sea level ignores land/water boundaries; the slider feels random Sea level was an absolute threshold on an unnormalized elevation field, fighting randomly-strengthed continent attractors Percentile sea level — sort elevations and cut at the Ocean % dial, giving the exact land fraction on every seed and making elevation signed around a true zero
"Weird continents" — straight borders slicing through one landmass Continent identity was the Voronoi cell of the nearest attractor, computed independently of the actual land Label landmasses by flood fill of connected land; continents become drifted fragments of one supercontinent, so identity is real history
Diffuse, blobby landmasses Continents were Gaussian blobs with a fractal-noise term too weak to disguise them Noise becomes the dominant term; tectonic fragments and ridge belts shape the outline; domain warp applied to the whole field
No rivers, biomes or terrain were possible at all Ocean did not exist as data — only land hexes were stored, so moisture, coasts, lakes and river mouths had nothing to flow through Every cell exists (ocean included) carrying elevation, temperature, rainfall and water state

Reference models it drew on, per its own spec: Whittaker biome classification (temperature × rainfall), priority-flood terrain hydrology, Potts/MRF relaxation for biome-boundary cleanup, and supercontinent-breakup tectonics for continent shape.

3 · Design decisions

Snapshot of .claude/DECISIONS.md, newest first — that file is authoritative and append-only. Three entries are recorded there.

hexworld-v2 as the intended map generator
Build procedural world generation as a standalone lab (hexworld-v2/) and adopt it as the project's intended map generator, replacing the hardcoded ASCII earthMap blueprint in js/state.js::generatePlanetMap(). Building it outside the game let it grow its own test suite (119 determinism-asserting tests) free of the game's DOM and state coupling, and it ships as a runnable demo on its own.
Grow procedural generation inside js/state.js — rejected: no test seam, and the game's state model would have to churn alongside the algorithm
Keep the ASCII blueprint permanently — rejected: a fixed world caps replay value, and territory seeds are already coordinate-based, so they can move
Hand-author more blueprints — rejected as unbounded manual work
PROVISIONAL — adopted in intent, unproven in the game. Not yet integrated; the wiring itself is unresolved, see §7.
Data-driven game content
Keep territory, unit and card definitions in js/data/ as plain data modules, separate from the systems that consume them — so balance tuning never requires touching combat or map logic
Inline stats into the systems — rejected: makes balance passes risky
FINAL
Civ V map architecture as a design reference
Study Civ V's map/territory architecture (see civ5_map_architecture_deep_dive.md) as input to the map design rather than copying the Axis & Allies board directly — a tile/territory architecture with real adjacency semantics serves "Risk with more depth" better than a fixed board
Direct board reimplementation — rejected as too constraining for the intended design
PROVISIONAL

The two older entries were reconstructed retroactively on 2026-08-12 from the repository's own structure and reference material; their dates are approximate and .claude/DECISIONS.md says so.

4 · The design

The two code trees

Two code trees live in this repo. They are not two generations, and they are not connected. grep -ri hexworld across js/, index.html, index.css and server.js returns nothing, and hexworld-v2 never mentions Axis & Allies or Iron & Crowns. server.js is a generic static server rooted at __dirname (server.js:24), so it happens to serve both — by accident, not by design. hexworld-v2 is a component-in-waiting, not a replacement that has landed.
TreeWhat it is
Root — index.html, index.css, server.js, js/** The live game. index.html:559 loads exactly one entry point, js/app.js. No package manifest, no build step, no dependencies.
hexworld-v2/ A self-contained map-generation lab with its own package.json, src/, test/, tools/ and docs/. 119 tests, all passing. Ships as one self-contained ~1.02 MB hexworld-v2/index.html with zero runtime network requests.

Turn structure and resources

A turn is a seven-step state machine in js/app.js:107:

Event -> Purchase -> Combat Move -> Combat -> Noncombat Move
      -> Senate Bidding -> End Turn -> (wraps back to Event)

Entering the Event phase draws a random global event from cardData.events and applies its modifiers. Economy runs on four resources — gold plus wood / metal / oil — with unit costs denominated in the latter three (js/data/unitData.js) and territory income and resource type assigned during map generation. Senate offices are won by bidding, and commanders can be bribed (js/politics.js).

World generation in the live game — the ASCII blueprint

This is the part most often described incorrectly, so it is stated plainly:

   |                                / jungle / mountain / tundra / (sea)

   |     seeds are hand-placed q/r pairs       js/data/mapData.js

It is not procedural. Every game plays the same world, because the world is a picture someone drew in characters. That ASCII blueprint is what hexworld-v2 is a candidate to replace — not js/map.js, which is rendering only and contains no world generation at all. Two earlier documents in this repo got that target wrong; it was corrected on 2026-08-16.

The renderer

js/map.js is a hybrid canvas/SVG engine: it builds hex paths, draws terrain from the textures in images/, and handles pan, zoom and hit-testing by geometry math rather than per-hex event targets. It is the largest and most coupled module in the tree (1,183 lines, rendering and geometry interleaved) and is listed as a known high-risk area in .claude/TESTING.md.

Why there is a server at all

server.js is 52 lines of zero-dependency Node serving the folder on http://localhost:8080. Its own header comment (server.js:2) gives the reason: ES modules cannot be loaded over file:// without tripping CORS. It holds no game state — whether this project ever becomes networked is an open question (§7).

hexworld-v2/ — the generation pipeline

Each stage is a pure, seeded module under hexworld-v2/src/procgen/; hexworld-v2/src/procgen/worldgen.js is the facade that orchestrates them.

tectonics -> elevation/sea -> climate -> hydrology -> biomes
          -> refine -> validate -> themes
  • Tectonics — worlds are made by supercontinent breakup. One landmass grows in pre-drift "plate space", cracks along a shared meandering rift network, and the fragments drift apart on the wrapped map. Because both sides of a rift are cut by the same curve, facing coastlines are conjugate — they visibly fit. Leading edges become active margins (coastal mountain arc + offshore trench, and the volcanic biome); trailing edges become passive margins (wide shallow shelf seas).
  • Elevation and sea level — signed elevation from tectonic crust plus fBm noise, domain-warped, with a polar fade. Sea level is a true quantile zero, so the Ocean % dial delivers the exact land fraction on every seed.
  • Climate — temperature from latitude insolation minus a mountain lapse rate; rainfall from a wind-ordered moisture sweep across trade/westerly/polar-easterly belts, with orographic uplift, leeward carry, and descending air that genuinely drains column moisture. Rain shadows and ~28° desert belts are emergent, not painted.
  • Hydrology — rivers flow along hex edges. Every grid corner is a junction; a priority-flood pass finds the water surface, each junction gets one seeded downhill outflow, and rainfall feeds flow accumulation down those chains. Width scales with √flux, so tributaries visibly merge into trunks. Starved closed basins become endorheic salt lakes or dry salt flats — rivers are allowed to die honestly in a desert.
  • Biomes and refine — a Whittaker-style table maps (temperature, rainfall) to biome, then dithering plus a Potts/MRF relaxation over a designer-editable affinity matrix absorbs single-hex speckle without erasing rain shadows.
  • Validate — every generated world must clear a quality floor (enough river mouths, enough distinct biomes, the requested continents actually present). A failing seed silently retries seed+1 and the stats bar states the reason.
  • Themes — six world personalities (Terran, Pangaea, Shattered Archipelago, Dune, Glacial, Primordial). Each is a bundle of dial defaults, a whole-world climate character, a palette re-skin, and its own acceptance rules, hashed into its own seed universe.

hexworld-v2/ — engineering invariants

These are load-bearing, regression-pinned, and the reason the lab's output is reproducible. Full text in hexworld-v2/CLAUDE.md (ten numbered invariants); the ones that most constrain future work:

InvariantWhy it matters
Purity — src/core.js and every src/procgen/ module stays pure and dual-environment: no DOM, no Pixi, no I/O, no Date.now(), no Math.random() It is why the engine can be tested headlessly in Node at all — and why it could be imported into the game without dragging a renderer along.
RNG substream discipline — all randomness flows through mulberry32 substreams salted off the world seed (N.substream(seed, "name")), never a shared sequential stream Adding a draw in one stage cannot shift every downstream stage's output.
Draw-order preservation — same (mode, seed, sizeKey, clusterR, dials, theme) ⇒ byte-identical world; generateProcedural replicates core.generate's five main-stream draws in the same order Keeps the hex lattice identical between Earth and Procedural mode at the same seed. Reordering draws silently invalidates every pinned regression.
Identity defaults, three layers — Earth mode is byte-preserved (seed 1 medium ⇒ totalLand === 1828); every dial's default ≡ omitting the option; the terran theme is the identity New dials and new themes cannot quietly change existing worlds.
Raw vs facade layering — generateProcedural stays raw and theme-less; themes, validation and seed+1 retry live only in the generateWorld facade Engine tests target the raw layer; the app calls the facade.
One self-contained deliverable — everything is inlined into hexworld-v2/index.html by tools/build.mjs, zero runtime requests, budget ≤ 1.3 MB (currently ~1.02 MB) That file and src/world-data.js are build artifacts — never hand-edit them.

Root game — manual regression checklist

The full checklist is in .claude/TESTING.md, grouped into Boot, Core loop, Systems, World generation and Data integrity. The world-generation checks are the ones easiest to break by accident:

  • All 26 seeds in js/data/mapData.js receive hexes — no empty territory.
  • Land/sea coastlines still match the earthMap blueprint (js/state.js:107-168) after any edit to it.
  • Every character used in earthMap has an entry in charToBiome.
  • Every territory in js/data/mapData.js has valid adjacency references; every unit referenced by game logic exists in js/data/unitData.js; every card in js/data/cardData.js has a handler.

7 · Open questions

Undecided, not requirements. Nothing here binds behavior. Snapshot of .claude/OPEN_QUESTIONS.md — five entries, all genuinely open. None of them is answered in this document.

  • How does hexworld-v2 connect to the live game? Adopted in intent, not wired in — the two trees share no code and no references. Replacing the ASCII blueprint means answering how a generated world gets 26 balanced, recognisable territories, since the seeds are currently hand-placed on Earth geography (Essen_Core, Rhine_Plains, …) and named after real places, which a random world cannot honour. It also crosses a module-format boundary (hexworld-v2 is CommonJS/UMD-lite, the game is ES modules) and a resolution one (hexworld's ~2.0k / 7.1k / 22.7k cells vs the game's 7,200). Options on the table run from importing src/procgen/** and generating at boot, to baking worlds offline as data, to keeping the Earth blueprint as default with generated worlds as a separate mode, to dropping the integration entirely. Owner: Miles + Minerva (architect). No target date.
  • Multiplayer model — local, or networked? server.js serves the client but there is no state-sync layer. Hotseat-with-a-static-server versus an authoritative server versus peer-to-peer changes the architecture of js/state.js substantially. Blocks any significant js/state.js restructuring. No target date.
  • How much of the Axis & Allies rulebook is binding? The rulebook PDF sits in the repo, but the stated intent is "similar to Risk but slightly more complicated," not a faithful port. Without a line, every rules question is a judgment call. Options: inspiration only / specific subsystems (combat odds, unit costs) track the rulebook / full fidelity. Blocks combat and unit balance work. Owner: Miles. No target date.
  • Map scale and performance budget. No territory-count ceiling and no turn-resolution time target has been set, so there is nothing to test map or combat performance against. Owner: Miles + Apollo (QA). No target date.
  • Persistence — is there a save game? No save/load path exists; game state lives only in the in-memory GameState instance, and a page reload starts a fresh game. Blocks nothing yet. Owner: Miles. No target date.

.claude/REQUIREMENTS.md carries a matching "To be filled in" list — target map size / territory ceiling, performance budget, multiplayer model, browser support floor, and save/load expectations. They are recorded there as explicitly undetermined, not as requirements, and should not be invented by an agent.
